    Feature Topics¶

    This page groups all 64 feature flags into 9 topics by the problem they solve. Each topic opens with the principle (what it is, what problem it solves), followed by a member table (one-liner + when to enable). For single-parameter lookup use the feature flags overview; for depth, each flag's detail page.

    1. MoE Communication & Compute Overlap¶

    Every MoE layer runs two collective communications: dispatch routes tokens to experts, combine gathers results back. Communication grows linearly with EP size and can dominate compute. The flags here do three things: fuse (merge dispatch/combine into one operator), overlap (hide communication behind compute on extra streams), and quantize (shrink communication bytes). MoE-only (DeepSeek/GLM/Kimi class) — no effect on dense models.

    Flag One-liner When to enable
    enable_fused_mc2 Fused MC2 dispatch/combine operator (0 off / 1 on / 2 MegaMoE) On per official model recipes; A5 MegaMoE requires SiTU models
    mc2_comm_alg dispatch/combine communication algorithm (fullmesh/hierarchy/fullmesh_v2) Cross-node MoE, per chip: hierarchy A2/A3 only, fullmesh_v2 A3 only
    combine_quant_mode Combine communication quantization (e.g. 4 = FP8) Cross-node combine bandwidth bottleneck, per official recipes (DeepSeek-V4 D node)
    enable_shared_expert_dp Run shared experts data-parallel across TP ranks TP>1 with high shared-expert share; trades memory for performance
    multistream_overlap_shared_expert Overlap shared-expert compute and communication on a dedicated stream MoE with shared experts; when TP=1 or shared_expert_dp is on
    multistream_dsv4_dsa_overlap DSA multi-stream overlap for DeepSeek V4 On by default; applies to DSV4 models
    multistream_engram_overlap Engram module multi-stream overlap A5-only by default; explicit value overrides
    enable_flashcomm1 FlashComm1 communication optimization for SP MoE Model Runner V1 only; use PCP on MRv2
    enable_prefill_mc2 Reserve MC2 token capacity for prefill batches P node (PD-disaggregated); officially a temporary switch
    mix_placement Mixed expert placement on the DP×TP plane Sender and receiver configs must match (RFork weight-transfer fingerprint)
    ~~enable_mc2_hierarchy_comm~~ Deprecated Use mc2_comm_alg="hierarchy" instead
    ~~enable_matmul_allreduce~~ / ~~enable_flashcomm2_parallel_size~~ / ~~multistream_overlap_gate~~ Removed See detail pages / version history

    2. Load Balancing & Scheduling¶

    EP's pain is routing imbalance: hot experts queue while cold ones idle. This family covers four layers: EP weight balancing (EPLB), PD-disaggregated scheduling (recompute/balance/short-request-first), batch-job scenarios, and RL sampling. Many are mutually exclusive — startup validates combinations and fails loudly on illegal ones.

    Flag One-liner When to enable
    eplb_config EPLB balancing config (dynamic_eplb / expert_map_record sub-keys) Standard concern for EP deployments; dynamic balancing also needs DYNAMIC_EPLB=true
    enable_force_eplb Force deterministic round-robin expert routing Performance analysis only — replaces real routing and invalidates outputs; never production
    scheduler_config Canonical aggregation layer for scheduling extensions Since v0.30.0 all scheduling keys are unified here
    recompute_scheduler_enable Recompute scheduling (recompute instead of storing KV on refill) PD-disaggregated D nodes only — startup error on P / mixed
    dyntra_lb_config DyntraLB dynamic load balancing PD-disaggregated D nodes only, DP>1; never on P
    enable_balance_scheduling Balanced scheduling PD-mixed only (A3 single-node / colocated)
    short_request_first_config Short-request-first prefill scheduling Ordinary / PD-mixed / P node; not supported on D nodes
    batch_job_sched_config Batch-job-aware scheduling Batch workloads; cannot combine with ShortRequestFirst
    ~~old top-level keys~~ Merged into scheduler_config since v0.30.0 Old keys still work in transition but warn

    Official guides: DyntraLB · ShortRequestFirst · Dynamic chunked pipeline

    3. KV Cache Quantization & Memory Formats¶

    KV cache is the #1 memory consumer in long-context serving. This family governs layout (NZ / T-major / per-block transpose), quantization (C8 sparse layouts, int8/mxfp8 — the latter via CLI value-domain patches), and offloading (sparse KV to DRAM) — cutting KV memory with no (or minimal) precision loss.

    Flag One-liner When to enable
    weight_nz_mode Weight NZ format (0 off / 1 quantized only / 2 incl. BF16/FP16) Follow official model recipes per weight format
    enable_kv_nz NZ layout for KV cache MLA models only (DeepSeek class)
    enable_transpose_kv_cache_by_block Per-block transposed KV cache (fused-op path) On by default; required by fused attention path
    sparse_kv_offload_config Offload sparse KV cache to DRAM Never on Prefill (official); D node per memory pressure
    ~~enable_sparse_li_c8~~ / ~~enable_sparse_sfa_c8~~ Removed Since v0.30.0 derived from --attention_config.indexer_kv_dtype / --kv-cache-dtype ∈
    ~~c8_enable_reshape_optim~~ / ~~hamming_sparse~~ Removed See version history

    Related engine arg: kv-cache-dtype value patches (int8/mxfp8)

    4. Graphs & Compilation¶

    Graph capture freezes a whole forward step into one replay, eliminating kernel-launch and CPU-scheduling overhead — decode steps (1 token per sequence) benefit most. The family splits into two layers: vLLM layer (--compilation-config, cross-platform) and Ascend platform layer (these flags: ACLGraph/Xlite and operator fusion). The platform layer arbitrates the final mode — don't let the two layers fight.

    Flag One-liner When to enable
    ascend_compilation_config Ascend graph compilation config (enable_npugraph_ex etc.) Official PD recipes enable npugraph_ex on D; P often runs eager
    xlite_graph_config Xlite graph mode (full_mode controls prefill capture) Supported models per official graph_mode guide
    ascend_fusion_config Fused-operator config (GmmSwigluQuant etc.) Per model recipes; most sub-keys default on
    ascend_warmup_config Startup warmup overlapping weight loading Large models to cut startup time

    Related engine arg: --compilation-config (all cudagraph_mode values) · official graph_mode guide

    5. PD Disaggregation & Parallelism¶

    PD disaggregation splits prefill (compute-bound) from decode (bandwidth/memory-bound) onto separate nodes that scale independently. This family covers long-context parallelism forms (PCP for prefill / DCP for decode), fine-grained TP (memory for concurrency on D), MLAPO layer-wise parallelism, and CPU binding.

    Flag One-liner When to enable
    enable_pcp_embedding_lmhead_weight_sharding Shard Embedding/LMHead weights within PCP groups Default on when PCP>1
    enable_pcp_o_proj_weight_sharding Shard O-projection weights within PCP groups Default on when PCP>1
    finegrained_tp_config Fine-grained TP (independent TP degrees for oproj/mlp/lmhead/embedding) PD-disaggregated D nodes only (oproj/mlp>1 startup-validated), with recompute scheduling + preempt offload
    enable_mlapo MLAPO layer-wise adaptive parallelism Decode nodes only in PD (official); consumes more memory
    mlapo_keep_prefill_weights Keep prefill weights on D nodes instead of freeing D-node local-prefill paths need it (issue #11882); memory for stability
    enable_cpu_binding Ascend CPU binding on ARM servers Widely enabled on both sides in official PD recipes
    profiling_chunk_config Dynamic chunked pipeline parallelism Requires PP>1; GLM5.2 evidences P node; incompatible with DyntraLB/balanced scheduling
    ~~enable_context_parallel~~ / ~~enable_dsa_cp~~ Removed Superseded by PCP (enabling dsa_cp on main errors with a PCP hint)

    6. KV Reuse & Pooling¶

    Two ways to "stop paying recompute for KV": KVPP splits redundant per-layer MLA/SFA KV across TP ranks within one node (same memory, longer context); KV pooling (Ascend Store) shares KV across nodes. Note pooling is not an additional-config flag — its entry is --kv-transfer-config.

    Flag One-liner When to enable
    enable_kvpp KV layer-wise parallelism across TP ranks Prefill node only (official); requires PIECEWISE graph mode
    kv_pool_range_debug Audit logging for KV pool layer-wise transfers Debug only; keep off in normal runs

    Pooling config → Engine args overview · KV pooling topic · official KV Cache Pool

    7. Speculative Decoding¶

    A small draft model predicts tokens that the large model verifies in one pass — trading acceptance rate for decode speed. This family governs dynamic speculation (adaptive draft length by load) and draft KV sliding window (draft attends to only the last N tokens).

    Flag One-liner When to enable
    dynamic_spec_config Dynamic speculative decoding config Fluctuating load where adaptive draft length pays off
    draft_window_size Draft KV sliding window (draft sees last N tokens) Long context + eagle3/dflash paths; output quality unchanged

    Related engine arg: --speculative-config · official speculative decoding guide

    8. Stability & Monitoring: Runtime Guard¶

    vLLM-Ascend's online anomaly detection and incident-response layer: it watches decode-time signals (token repetition, garbled text, non-finite logits, speculative acceptance-rate drift, etc.), writes structured reports on trigger, and can optionally dump request-level KV cache blocks. Everything is off by default with negligible overhead; open switches level by level when investigating.

    Flag One-liner When to enable
    runtime_config Startup overlay layer for runtime config Tune detectors/dump quotas online
    runtime_config_path Runtime Guard JSON path Config not at the default location
    runtime_config_hot_reload Hot-reload runtime config Change config without restart
    dump_config Inline msprobe dump config Integrating the msprobe debugger
    dump_config_path msprobe dump config file path Legacy option
    msmonitor_use_daemon msmonitor daemon mode Per monitoring deployment needs
    ascend_log_path vLLM-Ascend log path Default ~/ascend/log/vllm_ascend

    9. Training & RL¶

    RL training (rollout inference + weight sync) needs special inference-side cooperation. This family covers one-shot RL mode (force-disables inference-time optimizations, sets dev mode), global config refresh (reset Ascend config in training loops), and the rejection sampler (block/entropy two-level verification).

    Flag One-liner When to enable
    rl_config One-shot RL mode master switch When wiring RL training frameworks; forces weight_nz_mode=0 etc.
    refresh Refresh global Ascend config RLHF training loops / test cases resetting config each iteration
    rejection_sampler_config Rejection sampler (block / entropy verify) RL rollout sampling quality filtering

    Related engine args: RL family (--weight-transfer-config etc.) in engine args overview · official RL guide
